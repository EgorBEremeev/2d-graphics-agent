# Операционный контракт 2D-графики

Вся проектная агентская конфигурация и память ведутся на русском. Коммиты — без co-author. Вход в документацию — docs/README.md.

1. Осмотри задание и источник; определи операцию, ограничения, домен A (artwork), B (изделие) или P (страница) и итоговые файлы. Контракты — docs/agent/graphics-data-contracts.md. Комбинированную задачу раздели на A→A, A→B и A→P/B→P; производственные параметры относятся только к соответствующей стадии. Сохраняй оригиналы; преобразования выполняй на рабочей копии, когда они разрушают источник.
2. Выбери действительный маршрут в docs/agent/operations.md и docs/agent/capability-matrix.md, прочитай применимый domain skill. Сверь модель данных, необходимые части входа и поддержку операции выбранным интерфейсом. При совпадении входа и условий используй подтверждённый интерфейс без повторного discovery/help/version/probe.
3. Для нового или изменённого интерфейса уточни контракт и однократно проверь минимальную безопасную операцию. При отсутствии пригодного маршрута выполни discovery по имени и операции через официальные источники подходящих средств, проверь Windows и лицензию. Подготовку недостающих средств выполняй по docs/environment/setup.md. Сравни подходящие средства на одном небольшом входе, если выбор не решён имеющимися свидетельствами.
4. Существующий SVG направляй в native CLI или совместимый runner по матрице. Известный неподдерживаемый action пропускай сразу к зарегистрированному fallback.
5. Выполни графическую операцию. CLI/API/runners и headless render разрешены по умолчанию; интерактивный GUI/Computer Use — только по прямому разрешению пользователя. Просмотр готового preview допустим. Если требуется проектный стык, запиши отсутствующую операцию и проверенные альтернативы. Адаптируй пригодную существующую реализацию, сохраняя её рабочий downstream. Для узкой новой утилиты задай вход, выход, параметры, обработку ошибок и ограниченные тесты. Передавай пути, геометрию, подписи и другие данные конкретной работы через CLI/config.
6. При штатном ходе принимай промежуточные результаты без повторных хешей, DOM-diff, рендеров и отдельных отчётов. При ошибке или сомнительном эффекте проверь конкретное постусловие; при подтверждённом дефекте смени способ. Корректная идемпотентность допустима.
7. Перед сдачей проверь сохранённый итог соразмерно риску: вид/семантику и существенную геометрию; дополнительные проверки — при риске потери зон, отверстий, ID, ошибок меток, размеров или печати. Для нумерации используй один из альтернативных labeler-маршрутов; mapping и условия передачи в раскладку или компоновку бери из контракта A/B/P.
8. Обновляй матрицу при подтверждённом новом знании или изменении интерфейса. Отчёт содержит итоговые файлы, исполнителя, параметры и существенные ограничения. Отдельно укажи статус результата и состояние инструментальной возможности. PASS означает проверенный результат; FAIL — нарушение; UNPROVEN — нехватку наблюдений; BLOCKED — конкретный недоступный компонент или необходимое разрешение. Полный trace нужен для приёмки или диагностики дефекта.

Рабочие утилиты находятся в tools/, проверки — tests/. Для этапа приёмки сохраняй в artifacts/<YYYY-MM-DD_HH-MM-задача>/ компактный manifest, необходимые входы/происхождение, принятые результаты и свидетельства. SHA-256 применяй только там, где нужна проверка целостности; массовые описи временных файлов не нужны. Исторические отчёты сохраняй со своими artifacts, планы — docs/archive; рабочие сведения имеют один источник.

Временные профили и кэши создавай через TemporaryDirectory в игнорируемом .cache/graphics; постоянный профиль расширений один на проект вне artifacts. Перед завершением очисти служебные данные текущей задачи, проверь scoped diff и сохрани чужие изменения. Текст читай/записывай UTF-8 без BOM, команды должны быть совместимы с Windows PowerShell 5.1. Настройки trust/permissions и глобальную конфигурацию сохраняй.
