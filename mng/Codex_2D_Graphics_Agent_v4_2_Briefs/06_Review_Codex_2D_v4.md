# Техническое ревью Project Brief — Codex 2D Graphics Agent v4 (Refactor)

**Дата:** 11.11.2026  
**Объект:** `08_Project_Brief_Codex_2D_Graphics_Agent_v4_Refactor.md`.  
**Контекст:** `07_Project_Brief_Codex_2D_Graphics_Agent_v3.md`, `06_Review_Codex_2D_v2.md`, самостоятельные задания `01`–`05_Skill_Brief_*.md` из комплекта v3.  
**Метод:** документарное сопоставление постановок и их контрактов; локальный репозиторий, действительная конфигурация Codex, транскрипт Gum-Tree и исполняемые инструменты в рамках данного ревью **не проверялись**. Фактические версии и проявления багов приведены по тексту v4 и требуют подтверждения на целевой машине.

## 1. Итог

**Вердикт: REVISE BEFORE EXECUTION.** Концепция v4 обоснованна: нужно устранить принудительный вызов несовместимой обёртки, различить операционный протокол и реестр возможностей, признать программную компоновку допустимой графической операцией, контролировать фактический результат CLI и честно обозначать происхождение кода. Однако как исполнительная постановка v4 недостаточна: в ней отсутствует воспроизводимая схема обновления основного агента, неполны контракты данных, критерии проверки CLI частично неверны, а изменяемый реестр не имеет доказательной модели. Выполнение «в лоб» может формально привести к желаемой структуре файлов, но не к управляемому поведению Codex.

## 2. Что в v4 следует сохранить

1. **Разделение устойчивой политики, проектного протокола, маршрутов и информации об инструментах.** Инструментальные имена и версии действительно не должны выступать универсальными поведенческими директивами.
2. **Ограничение `cli-anything-inkscape` по реально подтверждённому входу.** По данным v4 его harness читает собственный JSON, а не произвольный внешний SVG; исходный `SKILL.md` внешнего пакета следует сохранить.
3. **Самостоятельный класс `Document Assembly`.** Сборка схемы, легенды, экспликации и выходного листа — отдельная операция, не равнозначная ни векторизации, ни тесселяции.
4. **Семантическая оценка там, где есть риск.** Код возврата ноль не доказывает изменение изображения, документа или структуры; но это не оправдывает обязательную проверку каждой штатной команды.
5. **Строгая атрибуция штатной команды, готовой проектной утилиты и вновь написанного кода.**
6. **Headless по умолчанию.** Уход из неудачного CLI прямо в GUI без явного согласования недопустим.
7. **Небольшие переиспользуемые интерфейсы вместо одноразового хардкода.** Задача на Gum-Tree не должна превращаться в общую конфигурацию графического агента.

## 4. Архитектурное решение

Рекомендуются четыре **слоя поведения/маршрутизации** и отдельный слой предметных контрактов и evidence. Это не пятый источник competing instructions:

- **Developer-role (активен после подтверждения загрузки):** идентичность, `reuse → adapt → build`, предметная координатная дисциплина, честная атрибуция, соразмерный итоговый контроль, право на ограниченную реализацию.
- **`AGENTS.md`:** исполнимый протокол выбора маршрута и ошибок; запрет самовольного GUI; условия создания переиспользуемого project CLI; обязанность пользоваться картой и register; сохранность данных; раздельные статусы выполнения.
- **Route map:** краткое соответствие *тип входа → операция → domain skill/категория исполнения → ожидаемый выход*, с явно альтернативными вариантами.
- **Capability matrix:** фактические интерфейсы, вызовы, проверенные границы, версия/машина, доказательства, fallback; **реестр данных, не инструкция высшего приоритета**.
- **Контракты:** artwork/manufacturing/presentation schemas с правилами перехода, независимые от того, в какой программе реализована операция.
- **Evidence:** fixtures, logs, сравнения, QA и transcript независимой сессии; никакая запись в matrix не заменяет raw evidence.

## 5. Изменение контура навыков

Привести к единой маршрутизации пять независимых мозаичных skills:

1. `sketch-mosaic-pre-vectorizer`: растр эскиза → зоны художественного SVG (A).
2. `photo-mosaic-pre-vectorizer`: фото физической кладки → восстановленные художественные зоны (A).
3. `tessellation-mosaic-generator`: художественные зоны (A) → физические тайлы (B), andamento и 1:1 prepress только по физической постановке.
4. `vector-svg-to-numbered-contours`: цветной SVG (A) → нумерованные контуры (A), ограниченная адаптация `paintbynumbersgenerator` с reuse downstream.
5. `inkscape-cli-mosaic-labeler`: альтернативный (не второй последовательный) путь SVG (A) → нумерованные контуры (A), headless `inkex/Shapely` runner при доказанной необходимости.
6. `document-assembly`: сборка/легендирование художественных схем (A→P) и отдельно, при необходимости, сборочных производственных листов (B→P) из готовых компонентов. **Не** восстановление областей и **не** создание плиток.

Для `cli-anything-inkscape` предусмотреть отдельное проектное сопровождение внешнего tool skill: оригинал read-only, `LOCAL_LIMITATIONS.md` и маршрутизация, не обещающая универсальной SVG-поддержки. Все исходные задания на skills должны задавать условия `available/not installed/not tested/blocked`, а не принудительно разрабатывать вторую систему, если первая уже принята.

## 6. Рекомендуемая приёмка

**G0** Ограниченная инвентаризация затронутых файлов/инструментов и Git status; **G1** корректная загрузка developer + AGENTS; **G2** cross-reference skills и совместимость маршрутов; **G3** два разнородных положительных и один отрицательный fixture компоновщика; **G4** одна новая сессия с двумя blind prompts (SVG labeling и Document Assembly); **G5** точечная A/B/P регрессия только если изменён соответствующий путь; **G6** scoped diff и краткое заключение с PASS/FAIL/UNPROVEN/BLOCKED. При FAIL исправлять дефектный компонент и повторять его тест, не всю последовательность.

**Недопустимо:** объявлять весь комплект skills реализованным только потому, что переформулированы задания на них; подменять проверку реального Codex правильностью текстов; опираться на обещанные команды вместо запущенных операций; программно изменять пользовательские настройки без согласования.

## 7. Статус исходных сведений

Факты об ограничениях `cli-anything-inkscape`, `paste-in-place` и содержимом `package_coloring.py` взяты из текста v4, который ссылается на приёмку Gum-Tree. Непосредственных результатов команд, исходников утилиты, полного транскрипта и содержимого рабочего репозитория в представленном материале нет. Поэтому описанное в этом ревью — оценка **качества постановки**, а не повторная техническая диагностика установленной среды.
