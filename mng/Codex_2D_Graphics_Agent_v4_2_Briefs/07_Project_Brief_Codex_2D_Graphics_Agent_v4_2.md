# Project Brief — Codex 2D Graphics Agent Configuration & Capability Architecture

**Версия:** 4.2 · **Дата:** 11 ноября 2026 г.  
**Исполнитель:** основной Codex в доверенном репозитории; преимущественно Codex в VS Code на Windows 10/11.  
**Рабочий проект:** `C:\gitCreative\solo-learn-mosaic`.  
**Тип задания:** рефакторинг и проверка действующей проектной специализации графического агента. Это **не** новая универсальная графическая программа и **не** поручение реализовать все предметные skills заново.

## 1. Цель и измеримый итог

Сформировать устойчивую и проверяемую конфигурацию **основного** Codex как оператора 2D-графики. В новой независимой сессии агент должен самостоятельно распознавать тип графической операции, выбирать применимую готовую компетенцию, правильно использовать действительные CLI/API, создавать редактируемые результаты, различать художественные координаты изображения и физическую геометрию изделия, обеспечивать правильность итогового результата и адресно проверять сомнительные операции, не устраивая повторное QA каждого промежуточного шага; закрывать доказанный узкий функциональный пробел проектной утилитой.

В ходе работы нужно:

1. Проверить и согласовать две реально активные модели инструкций основного агента: `developer_instructions` в доверенном проектном `.codex/config.toml` и `AGENTS.md`.
2. Разделить нормативное поведение, процесс маршрутизации, проверяемые возможности среды, контракты графических данных и результаты испытаний.
3. Устранить неверную маршрутизацию существующих SVG на обёртку, принимающую только собственный JSON-проект; не изменять исходный сторонний skill без необходимости.
4. Ввести поддерживаемую операцию **Document Assembly**: параметризованное объединение художественной схемы, палитры, экспликации и элементов страницы без имитации GUI.
5. Превратить имеющийся `tools/coloring/package_coloring.py` (если он существует) в узкий воспроизводимый интерфейс компоновки без зависимостей от конкретной работы, с сохранением проверяемого прежнего функционала.
6. Согласовать маршруты **пяти самостоятельных мозаичных навыков** и их интерфейсы. Полная разработка отсутствующего навыка остаётся отдельным заданием; действующий навык не заменяется фиктивной новой реализацией.
7. Подтвердить результат ограниченным набором функциональных испытаний изменённых интерфейсов и целевым blind-проверочным заданием для основного Codex без подсказок имён программ/skills; не превращать каждую пользовательскую задачу в повторную приёмку конфигурации.

**PASS измеряется наблюдаемой деятельностью агента и правильностью графического результата.** Файлы инструкций, перечень установленного ПО, код возврата 0, наличие SVG или добавленная строка в матрице сами по себе не являются свидетельством успеха.

Наличие этих путей **не гарантировано** — фиксировать `PRESENT / ABSENT / UNKNOWN`, не создавать дубликат вместо поиска.

Проверить версии и интерфейсы установленных инструментов: Inkscape CLI, `cli-anything-inkscape`, ImageMagick, Potrace, VTracer, `inkex`, `Shapely`, `vpype`, `ezdxf`, Python и зависимости компоновки; Node/toolchain — только если проверяются существующие Node-адаптеры. Не предполагать, что сторонний wrapper имеет функции нативного приложения.

**Scope:** преимущественно файлы и зависимости данного репозитория. Всякое изменение базовой инструкции через `model_instructions_file` запрещено без отдельного экспериментального задания.

Действующие пользовательские изменения в Git не перезаписывать. Перед началом записать status/branch, перед коммитом проверить scoped diff. При неопределённости прав — `BLOCKED` с точным описанием нужного согласования; не подменять разрешение обходом ограничений.

## 3. Целевая четырёхуровневая архитектура конфигурации

Результат рефакторинга — **четыре разных по назначению уровня управления поведением основного Codex**. Их необходимо проектировать как систему: верхний уровень определяет общие принципы инженерного мышления; следующий — порядок действий в данном проекте; третий — способы маршрутизации типов графических операций; четвёртый — фактически доступные и проверенные средства. Уровни различаются **смыслом, адресатом, степенью изменчивости и правом устанавливать правила**, а не расширением файлов или именем ключа конфигурации.

Уровень 3 отвечает на вопрос *какой вид решения нужен*, уровень 4 — *какое конкретное средство в текущей среде действительно умеет это делать*. Нижние уровни уточняют верхние, но не изменяют их политики. При расхождении приоритет имеет вышестоящее правило; противоречие исправляется в соответствующем источнике, а не обходится через дополнительную копию инструкции.

**Вспомогательные документы не образуют пятый и шестой уровни.** `docs/agent/graphics-data-contracts.md` задаёт схемы и геометрические инварианты художественного домена A, производственного B и компоновочного P; fixtures/тесты/отчёт приёмки являются доказательной базой. Различие A/B, установленное приоритетной политикой, сохраняется; P — отдельные координаты представления страницы, а не замена физического B и не разрешение вносить миллиметры в художественную геометрию.

**Каноничность и фактическая активация.** Источником авторского текста уровня 1 является `docs/agent/graphics-developer-instructions.md`; реально действующий текст должен находиться в загруженном `developer_instructions` доверенного проектного `.codex/config.toml`. Источником уровня 2 служит `docs/agent/graphics-model-behavior.md`; реально действующее содержание должно присутствовать в применимом для рабочего каталога `AGENTS.md`. Совпадение или контролируемая генерация этих пар — лишь техническая предпосылка. Нельзя считать специализацию выполненной только потому, что файл создан, ключ TOML существует или его содержимое синтаксически корректно.

## 4. Требования к содержанию обновляемых файлов

Каждый из четырёх уровней проектируется **по нижеследующим требованиям**, а не составляется путём копирования формулировок этого брифа в новый файл. Перечни ниже определяют функции, поведение и границы документа. Исполнитель обязан написать собственный связный, внутренне непротиворечивый и пригодный к непосредственному применению нормативный текст. Готовая формулировка одного пункта брифа не считается готовой инструкцией модели.

### 4.1. `docs/agent/graphics-developer-instructions.md` и `.codex/config.toml` — Конституция мышления

**Обязательное действие:** заново проанализировать действующий `developer_instructions` и подготовить полноценную редакцию текста уровня 1. Это **содержательная переработка специализации основного агента**, а не косметическое удаление упоминания одного инструмента, вставка краткого слогана, перенос ссылки в документацию или минимальный патч прежнего текста. Существующие корректные правила можно сохранить по смыслу, но конечный документ обязан покрывать весь контракт ниже. Решение о формулировках принимает исполнитель на основании требований, а не за счёт копирования пунктов как готовых строк промпта.

**Требования к содержанию:**

1. **Инженерная идентичность и предмет ответственности.** Главный Codex действует прежде всего как оператор создания и преобразования графических артефактов, умеющий планировать художественные и геометрические операции. Программирование — вспомогательный способ устранения доказанного функционального пробела, а не универсальный первый ответ на графический запрос. Skills, внешние средства и возможные subagents — исполнители/компетенции, но не замена специализации главной сессии.
2. **Единица мышления и классификация.** Агент должен раскладывать входной запрос на графические преобразования и требуемые итоговые артефакты: реконструкцию изображения, редактирование векторной геометрии, семантическую разметку, пространственный анализ, компоновку листа, производственную геометрию, подготовку выпуска. Классификация определяется содержанием и назначением операции, а не расширением файла или наличием удобного языка программирования. Она должна приводить к осмысленному плану исполнения, не к формальному перечислению компетенций.
3. **Нормативный процесс выбора средства.** До реализации агент определяет достаточность уже известных методов и проектных компетенций; выбирает проверенный маршрут по правилу **`reuse → adapt → build`**. `reuse` — применение совместимого существующего инструмента; `adapt` — использование доступной функциональности с минимальной адаптацией; `build` — разработка узкого недостающего средства после выявления реального интерфейсного/геометрического пробела. Само наличие трудности, неудача первого вызова или привычка писать код не являются доказательством необходимости `build`. При наличии применимого проверенного средства повторное исследование всех альтернатив не требуется.
4. **Цикл графической работы.** Осмыслить исходное изображение/геометрию и референс; установить ожидаемую семантику областей, границ, преобразований и физического назначения; определить критерии готового результата; применить действительное графическое средство; получить пригодный к использованию и редактированию артефакт; проверить существенные свойства итогового результата; изменить метод при доказанном дефекте. Не считать выполнением задачи установку инструмента, чтение `--help`, составление плана, запуск теста без графического выхода или декларацию об успешном преобразовании.
5. **Координатная дисциплина.** Художественная геометрия определяется исходным изображением/художественной композицией; физическая производственная геометрия — реальными размерами, допусками, элементами изготовления и заданным преобразованием масштаба. Нельзя автоматически переносить параметры изделий, размеры элементов, швы и требования печати на предварительную художественную реконструкцию или нумерацию областей. Размещение художественного результата на странице отдельно отождествлять с его производственным масштабированием запрещено. Любой переход между координатными областями должен быть осознанным и прослеживаемым.
6. **Результат и соразмерный контроль.** Ответственность агента — за фактически полученные графические результаты, сохранение их смысловой и геометрической корректности, достаточную редактируемость и соответствие заданию. Проверка конечного результата необходима по значимым требованиям, с учётом критичности топологии, метрических допусков или подготовки выпуска. **Не устанавливать обязательный контроль каждой промежуточной операции:** подтверждённые маршруты исполняются без постоянных хеширований, DOM-diff, повторных рендеров и журналов; диагностика включается при неизвестном интерфейсе, признаке отказа или конкретном высоком риске.
7. **Честная атрибуция и границы утверждений.** Различать действие штатного средства, ранее существовавшей проектной утилиты и кода, созданного при текущем исполнении. Не выдавать собственный скрипт за встроенную функцию стороннего редактора, декларативную команду — за реально выполненную операцию, а код возврата — за доказательство качества. Не маскировать отсутствие испытания под `PASS` и не заменять техническую аргументацию некритичным согласием с любым замечанием.
8. **Воспроизводимость и эволюция без инструментальной привязки.** Использовать сведения о доступных маршрутах и проверенных возможностях проекта; новые подтверждённые ограничения и пригодные к повторному использованию утилиты должны становиться доступными будущим задачам. Общий принцип фиксируется здесь, тогда как конкретные инструменты, версии, дефекты и инструкции регистрации описываются нижними уровнями.
9. **Границы полномочий.** Уважать доверенную область проекта, исходные пользовательские данные, действующие ограничения запуска и разрешений; не прибегать к несанкционированному GUI/Computer Use, системной установке или изменению глобальной конфигурации ради удобства обхода проектного задания.

**Жёсткая граница уровня 1:** в окончательном содержимом `developer_instructions` и его каноническом источнике отсутствуют названия конкретных приложений, обёрток, CLI, библиотек, языков программирования, форматов файлов, команд, версий, машинных путей, имён текущих задач и локальных известных багов. Эти данные не являются «подробностью» Конституции мышления: они относятся к уровням 2–4. Названия самих координатных областей и абстрактных операций допустимы. Не переносить в `developer_instructions` таблицу инструментов, route map или подробный рабочий регламент.

**Требования к результату редактирования:**

- Авторский документ — **полноценная самостоятельная инструкция**, а не бриф, комментарии к нему, список заметок или набор полуготовых фраз. Текст должен определять реальное поведение главного агента при произвольной новой 2D-задаче, даже если она не относится к мозаике.
- Актуальный текст разработчика нужно **действительно заменить/согласовать** в активном проектном ключе `developer_instructions` доверенного Codex, не оставив две конфликтующие редакции. Патч только документации без обновления runtime не является выполнением.
- Не удалять другие ключи существующего TOML и не подменять developer-role настройками subagent или `model_instructions_file`.
- Сопоставить прежний и новый тексты **по девяти смысловым требованиям**, кратко фиксируя пробелы старой версии и то, как новая их закрывает. Проверять именно содержание, а не количество изменённых байтов/строк. Если некоторый пункт ранее был выполнен полностью — не нужно искусственно менять его текст; но совпадение пары фраз не освобождает от остальных требований.
- Проверить корректность TOML и фактическую загрузку инструкции **основной сессией**. На независимой контрольной графической задаче агент должен проявить полную цепочку выбора и исполнения, а не просто назвать себя графическим специалистом. Такая поведенческая приёмка проводится в специально выделенном этапе, не после каждого пользовательского задания.

**Критерий приёмки 4.1:** нормативный текст покрывает все указанные функции, не содержит нижнеуровневых привязок, реально активен в developer-role главного Codex и приводит к наблюдаемой графической специализации. Отсутствие программных названий или валидность TOML **по отдельности недостаточны**.

### 4.2. `docs/agent/graphics-model-behavior.md` и `AGENTS.md` — Операционный протокол

Разработать **полноценную проектную инструкцию выполнения**, отличающуюся по функции от Конституции мышления. Она задаёт действия агента в доступной среде и ссылочную дисциплину нижних документов, но не копирует ни саму Конституцию, ни всю capability matrix. Её содержание должно быть достаточно конкретным, чтобы агент мог начать и завершить обычное графическое задание без внешних подсказок; при этом для выполнения специализированной операции он вправе читать адресно соответствующую карту и skill.

**Обязательные требования к содержанию:**

1. **Начальная классификация запроса.** Определять тип исходных данных, художественное/производственное/компоновочное назначение, ограничения и итоговый контракт. Для комбинированных задач явно разделять стадии A→A, A→B, A→P/B→P и не переносить производственные параметры в художественную фазу.
2. **Выбор по карте, затем по возможностям.** Сначала установить класс операции по `docs/agent/README.md`, затем найти совместимый и уже подтверждённый исполнитель в `docs/agent/capability-matrix.md` и при необходимости открыть соответствующий Domain/Tool Skill. Если контракт пригоден для текущего входа, применить его без постоянного `--help`, переинвентаризации среды и пробных запусков. Сама ссылка на skill не доказывает его доступности или функциональности.
3. **Селективный входной контроль (Interface Gate).** Сверять существенные свойства входа с реальным интерфейсом выбранного средства: контейнер/модель данных, наличие требуемых частей, поддерживаемость операции и применимость к текущему режиму. Не подавать существующий внешний документ в обёртку, рассчитанную на её собственный внутренний проект, только на основании названия редактора или расширения файла. Подтверждённую несовместимость из реестра учитывать напрямую, без воспроизведения известного сбоя.
4. **Исполнение и адресная диагностика результата.** Разрешать штатный CLI/API/headless-runner путь. Код завершения `0` сам по себе не доказывает графический эффект, однако обязательная проверка мутации после **каждой** команды запрещается как общий протокол. Для неизвестного интерфейса — один минимальный пробный вызов при необходимости; для явного сбоя или подозрения на `NO-OP` — одна проверка **конкретного ожидаемого признака**; для подтверждённой ошибки — переход к известному fallback. Неизменность файла может быть корректной идемпотентностью; изменение хеша/размера может не иметь отношения к запрошенному действию.
5. **GUI и полномочия.** Интерактивное GUI/Computer Use не запускать без прямого разрешения пользователя. Невозможность некоторой headless-команды не считается разрешением перейти в GUI. Разрешённые просмотр итогового изображения или headless-рендеринг не превращаются в обязательную GUI-фазу.
6. **Сохранность и доменные границы.** Не разрушать исходники; сохранять редактируемую графику, корректные единицы, системы координат, топологию и связи метаданных, если они существенны для задачи. Варьировать глубину проверки по фактическим рискам результата: обычный художественный лист, нумерованные контуры и производственный шаблон требуют разных доказательств.
7. **Narrow Gap Policy.** Если средства действительно не покрывают необходимую операцию, допустима **узкая** проектная CLI-утилита с определёнными входом, выходом, параметрами, корректной обработкой ошибок и минимальными тестами. Параметризовать пути, геометрию компоновки, размеры, отступы, подписи и другие job-specific свойства; не закреплять данные одного рисунка непосредственно в коде и не изображать собственный скрипт как команду внешнего приложения. Для адаптации проверенного алгоритма сохранять его реализованный downstream, если он годен.
8. **Живая память среды.** По завершении задачи обновлять `docs/agent/capability-matrix.md` **только** при новом, значимом и подтверждённом ограничении/изменении интерфейса либо при создании/изменении принятой проектной утилиты. Фиксировать точное условие, доказательство и fallback. Не добавлять декоративные записи, повторные наблюдения штатной работы и длинные логи команд. Обновление входит в разрешённый scoped-коммит вместе с кодом, если коммит предусмотрен.
9. **Финальный контроль и отчёт.** Проверять готовый артефакт по критическим требованиям, а не доказывать все промежуточные шаги заново. Отчёт должен указывать действительного исполнителя, полученные файлы, существенные ограничения и честный статус; отказ от инструмента объяснять технической причиной, когда она повлияла на решение. Не включать отчёт о выполнении каждой операции при отсутствии дефекта.

**Граница уровня 2:** это *операционный договор*, а не список доступных бинарников или версия CLI-harness. В нём допустимы относительные пути нормативных проектных документов и указания, как ими пользоваться, однако конкретные quirks и состав installed toolchain находятся в реестре. Ссылки на нижние документы должны быть рабочими; удалять из AGENTS самодостаточный алгоритм в пользу «см. README» запрещено.

**Критерий приёмки 4.2:** файл `AGENTS.md` действительно применяется в рабочей директории главного Codex; содержит все девять функций, не дублирует developer-role и не навязывает ритуального QA. Если проект имеет вложенные `AGENTS.md`, проверить приоритет реально загружаемых правил и устранить их противоречия в пределах разрешённого scope.

### 4.3. `docs/agent/README.md` — Карта маршрутов по классам операций

Перестроить карту **по семантическим типам действий**, сохранив различие между технологическим классом, координатной областью, предметной компетенцией и конкретным инструментом. Реестр установленного ПО — **не** маршрутная карта. Для каждого класса должна быть запись с полями: **смысл задачи/триггеры → ожидаемый вход → координатный домен → класс операций → класс исполнителя или предметный skill → выходной контракт → условия выбора и fallback → существенная проверка готового результата**. В карту не переносить версии бинарников, параметры их вызова и детальные воспроизведения багов.

**Обязательные маршруты:**

1. **Семантическая реконструкция и трассировка.** Исходники: линейный эскиз/орнамент либо фотография физической кладки. Результат: очищенная художественная композиция с определёнными границами и замкнутыми зонами. Домен — **A, координаты изображения**. Класс средств — очистка/сегментация растра, трассировка границ, восстановление векторных областей; существующие `sketch-mosaic-pre-vectorizer` и `photo-mosaic-pre-vectorizer` используют разные условия входа. Производственные плитки/швы и физические размеры в этот маршрут не включать.
2. **Деструктивная и топологическая модификация путей.** Исходник: уже существующая векторная геометрия, требующая Boolean, упрощения контуров, конвертации обводки, исправления топологии и аналогичных действий. Домен определяется **смыслом** исходника (A или B, иногда P), а не самим типом документа. Класс исполнителя — прямой графический engine/CLI либо подтверждённый векторно-геометрический runner, поддерживающий редактирование **существующих** данных. Выход — изменяемая геометрия с сохранением нужных ID/связей; не путать с генерацией простых примитивов с нуля.
3. **Пространственный анализ и разметка.** Исходник: векторные художественные зоны, требующие поиска пригодных областей размещения, проверки видимости, выносок, нумерации и согласования палитры. Домен — **A** до явного производственного перехода. Класс исполнителя — подтверждённый геометрический раннер с анализом видимых областей. Для нумерации `vector-svg-to-numbered-contours` и `inkscape-cli-mosaic-labeler` — **альтернативные**, а не обязательные последовательные этапы. Результат — нумерованная схема, стабильная карта соответствий, без самопроизвольной модификации художественных зон.
4. **Компоновка и легендирование (`Document Assembly`).** Исходник: готовая схема/раскладка, палитра, легенда, экспликация и layout-манифест. Домен — **A→P** (обычный лист с художественной схемой) либо **B→P** (представление физической раскладки на странице). Класс исполнителя — параметризованный проектный компоновщик и реальный headless-рендерер; результат — итоговый редактируемый лист/листы и экспорт. Объединение документов нельзя подменять headless-операцией, зависящей от GUI clipboard, когда такая операция уже установлена как ненадёжная. Компоновка не является производственной тесселяцией и сама по себе не гарантирует масштаб 1:1.
5. **Производственная дискретизация и prepress.** Исходник: принятая художественная геометрия плюс **явно заданные** физические размеры/допуски изделия, размеры элементов и швов, параметры направления укладки; при подготовке печати — отдельный print profile. Маршрут **A→B** формирует реальную физическую раскладку тайлов, **B→P** готовит листы с корректным масштабом, областями страницы и требованиями выпуска. Классы исполнителей — тесселяция, производственная геометрия, средства физической проверки и prepress. Не подменять заданные криволинейные направляющие прямоугольной сеткой; не выдавать подпись о размере за проверенный масштаб.

**Дополнительные операции** (CAD/технические чертежи, экспорт, простой векторный монтаж, подготовка preview и пр.) включить, если они реально покрываются текущей специализацией; для них действуют те же поля и принцип разграничения. Дополнительные строки не должны уничтожать перечисленные пять классов или смешивать их по признаку «всё работает с одним форматом».

**Стыковка карты:** для каждого класса зафиксировать ссылку на действительный контракт A/B/P и соответствующие Domain Skills/проектные ресурсы; конкретный установленный инструмент агент определяет уже по capability matrix. При отсутствии подходящего исполнителя карта указывает процедуру поиска или допустимый fallback, **не** обещает наличия несуществующего бинарника. Не дублировать в `AGENTS.md` полную таблицу маршрутов.

**Критерий приёмки 4.3:** по произвольному описанию операции можно однозначно определить нужный домен, вид исполнителя и ожидаемый контракт, не начиная с имени программы; Document Assembly различим от тесселяции и prepress, а два labeler-маршрута не запускаются механически один за другим.

### 4.4. `docs/agent/capability-matrix.md` — Живая матрица возможностей

Создать/переработать **реальный, пригодный для следующей сессии Codex реестр**, а не декларацию о том, что реестр когда-либо будет пополнен. Две обязательные секции: **A — External Tools & Harnesses** и **B — Project-Built Tools & Runners**. Записи должны позволять без повторного discovery понять, подходит ли инструмент для конкретного входа и операции. Единица записи — *проверяемая возможность в определённых условиях*, а не только название установленной программы.

**Минимальные поля:** инструмент/владелец; версия и среда, к которой относится наблюдение; допустимый формат/модель входа; фактические операции и выходы; способ invocation или указатель на contract/help; статус подтверждения с датой и источником; ограничения `quirks` с условиями воспроизведения; допустимый fallback; происхождение («внешняя программа», «внешняя обёртка», «существовавшая проектная утилита», «создано/адаптировано в текущем исполнении»). Учитывать `DISCOVERED`, `INSTALLED`, `PROBED`, `VALIDATED`, `UNSUPPORTED`, `BROKEN`, `STALE`, `NOT_TESTED`; историческое наблюдение не переписывать молча в `VALIDATED` текущей среды. Для записей из исходной документации прикреплять существующее свидетельство, а не воспроизводить известный отказ ради новой строки лога.

**Стартовое наполнение секции A (обязательно, с сохранением исходных технических фактов и оговоркой об их локальной применимости):**

- **`inkscape.com` — исходная зафиксированная версия 1.4.4.** Отдельные возможности: `path-union`, `path-split`, `path-flatten`, `--query-all`, экспорт PNG/PDF. Отдельное конкретное ограничение: `paste-in-place` в зафиксированном headless-сценарии возвращал код `0` без вставки. Это не доказательство отказа всех действий Inkscape и не общее правило о любых SVG. Для компоновки документов маршрутизировать на project Document Assembly.
- **`cli-anything-inkscape` — исходная зафиксированная версия 1.0.1.** Совместимый сценарий: создание простых фигур/текста в собственной JSON-проектной модели обёртки. Несовместимый сценарий: чтение, парсинг и модификация уже существующего внешнего SVG, при передаче которого наблюдался `JSONDecodeError`. Boolean-действия в соответствующей реализации обозначены `Placeholder`, их нельзя учитывать как подтверждённую геометрическую операцию. Не отождествлять wrapper с полным функционалом нативного приложения.
- **`VTracer` (0.6.15), `Potrace` (1.16), `inkex` (1.4.0), `Shapely` (2.2.0), `vpype` (1.15.0), `ezdxf` (1.4.5).** Для каждого обозначить реальные классы входов/выходов, доступные операции и границы применимости. Не считать версию и присутствие библиотеки доказательством любой произвольной операции. Если сведения в репозитории уже подтверждены — переиспользовать существующие evidence; при отсутствии нужных сведений указать неизвестное, не запускать массовый retest без задачи.

**Стартовое наполнение секции B (обязательно по фактическому состоянию репозитория):**

- **`tools/extensions/mosaic_labeler.py`** — топологический анализ видимых областей, поиск точек размещения (`polylabel`), выноски, номера, привязка к метрикам текста; зависимости/интерфейсы `inkex`, `Shapely`, `inkscape.com --query-all` там, где они реально используются. Разделить подтверждённые и неподтверждённые операции.
- **`tools/inkscape/precise_distribution.py`** — подготовка точного распределения, включая линейную аппроксимацию кривых с параметром допуска `tolerance`; указать реальные входы, выходы и пределы точности/применимости.
- **`tools/coloring/package_coloring.py`** — компоновка рисунка, палитры и итогового листа из данных задания; после рефакторинга отметить новый параметризованный CLI, входные манифесты, экспорт и зависимости (`lxml`, headless renderer при наличии). До успешной приёмки не объявлять новый контракт `VALIDATED`.

**Порядок ведения и стоимость:** при появлении нового значимого ограничения или принятого проекта агента дописать/актуализировать **только затронутую запись**, с кратким наблюдаемым основанием и применимым fallback. Изменение среды помечает затронутые записи как требующие перепроверки при следующем реальном применении; не обнуляет весь каталог. Штатное успешное выполнение с уже валидированным интерфейсом **не порождает** обязательную строку, хеш, подробный trace или дополнительный тест. Ничего не коммитить как «успешное свойство инструмента», если подтверждён только его `--help` или наличие файла.

**Критерий приёмки 4.4:** агент может выбрать подходящий конкретный CLI/runner по допустимым входам и операциям, обойти известные дефекты без бесполезной попытки, отличить стороннее средство от самописной утилиты и увидеть, какие утверждения подтверждены, а какие требуют проверки. Реестр не разрастается от каждого рядового запуска.


## 5. Контракты графических данных и единиц

**A — Artwork / image geometry.** Изображение, растр, художественные замкнутые области, палитра, номера цветов. Координаты исходного изображения или нормализованного `viewBox`, явная матрица raster↔SVG. Нет обязательных мм, плиток, швов, печатных полей. Типовые outputs: `artwork_regions.svg`, `artwork_regions.manifest.json`, `structural_layout.svg`, `palette_map.json`.

**B — Manufacturing / tile geometry.** Физическая форма изделия, тайлы, andamento, швы, минимальные допустимые элементы, размеры и допуски в мм, карта `A→B`. Outputs: `scaled_artwork.svg`, `scale_mapping.json`, `flow_lines.svg`, `final_layout.svg`, `tiles_manifest.json`. Масштаб 1:1 осмыслен **относительно реального размера изделия**, а не атрибута `width` на любом SVG.

**P — Presentation / document coordinates.** Координаты страницы/листов, компоновочные панели, легенды, экспликации, поля, заголовки, стили и экспорт. Mapping `A→P` — размещение художественной схемы в листе, **не** присвоение размерности плитке. Mapping `B→P` — производственный лист с явным физическим соотношением; только при заказе print profile `1:1` нужен контроль страницы/PDF boxes, разбиения листов и запрет скрытого `fit-to-page`.

Формат (`SVG`, `PDF`, `PNG`, `DXF`) и домен — независимые признаки: SVG может быть художественным, производственным или документным; PDF не обязательно в масштабе изделия. Объединение A+легенда в P не должно изменять исходный artwork или тайлы.

**Общий контракт зоны:** сохранённые `zone_id`, `color_id`/стабильный `palette_id`, геометрия замкнутых видимых контуров, правила `transform`, `fill-rule`, holes, CSS inheritance, clipping и корректная карта происхождения. Разные несмежные зоны одного цвета не сливаются из-за совпадения palette_id. У B появляется `tile_id`; `zone_id` **никогда не заменяет** `tile_id`. Для неподдержанной SVG-конструкции требуется нормализация проверенным инструментом или диагностический отказ.

**Общий контракт манифестов:** `schema_version`, `source`, `coordinate_domain`, `viewBox` либо явный physical/page extent, `objects` с устойчивыми IDs и преобразованиями, provenance исполнителя/версии, параметры преобразования, предупреждения и `qa_ref`. Конкретные обязательные поля и пример JSON зафиксировать в `graphics-data-contracts.md` и прогнать валидатор на 2–3 реальных fixtures. Не переименовывать существующие принятые поля без совместимого migration/alias.

## 6. Карта операций и маршрутизация

| Операция | Тип входа → выход | Домен | Исполнитель / маршрут | Критерий готового результата / особый риск |
|---|---|---|---|---|
| Очистка линейного эскиза, восстановление зон | raster sketch → `artwork_regions.svg` | A | `sketch-mosaic-pre-vectorizer` → проверенный raster/trace/vector CLI | Overlay, закрытость, topology, отсутствие физ. offsets |
| Реконструкция с фотографии реальной кладки | mosaic photo → artwork regions | A | `photo-mosaic-pre-vectorizer` → raster filtering/segmentation/vectorization | Сохранность художественных масс, не повторить старые швы |
| Стандартное векторное редактирование | SVG paths → корректный SVG | A/B/P по задаче | Нативный проверенный CLI vector engine или проектная геометрическая утилита | Выполнение заданного преобразования; DOM/geometry/render — только при риске или признаке отказа |
| Нумерация цветных областей — маршрут 1 | color SVG → `structural_layout.svg`, `palette_map.json` | A | `vector-svg-to-numbered-contours` (adapted upstream pipeline, если доступен) | Стабильность палитры, область метки, unchanged contours |
| Нумерация цветных областей — маршрут 2 | color SVG → тот же контракт | A | `inkscape-cli-mosaic-labeler` (headless inkex/geometry runner, если доступен) | Сравнительное QA, не вызывать оба подряд |
| Производственная раскладка | artwork → tiles and manifest | A→B | `tessellation-mosaic-generator` | Размеры/швы в мм, andamento, отсутствие пересечений и потерь |
| Компоновка листа и легенды | готовая схема + palette/manifest/layout → листы и preview | A→P / B→P | `document-assembly` / `tools/coloring/package_coloring.py` после рефакторинга | Полнота legend, page bounds, сохранность геометрии, финальный render |
| CAD/техническая графика | точные конструкции/размерный чертёж | B или самостоятельный physical CAD | проверенный CAD CLI/API, доступный tool skill | Размерная точность, замкнутость, экспорт DXF/SVG |
| Prepress/export | готовая художественная или физическая схема → PDF/PNG | P, при необходимости B→P | проверенный export/render CLI | PDF boxes, scaling, fonts, страницы, crop/bleed |
| Неизвестная операция | исходник и требуемое действие | определить | discovery → сравнение → probe → reuse/adapt/build | факт вызова, capability evidence и postcondition |

**Приоритет** route map не равен статическому приоритету какой-либо программы. Из двух альтернативных labelers в одном job выбирается **один**, по установленности, совместимости, сохранению геометрии и измеренной стоимости/качеству. При отсутствии полезного эффекта не создавать skills только ради числа.

## 7. Исполнение, контроль результата и диагностика отказов

**Проверка каждого вызова запрещена как универсальная политика.** Для подтверждённого маршрута, если вход попадает в известную область применимости и инструмент не сообщает об ошибке, агент выполняет последовательность без промежуточного SHA-256, сравнения размеров, DOM-diff, независимого рендера и отдельных отчётов по каждой операции. Нельзя превращать один headless `NO-OP` в глобальную обязанность перепроверять все графические CLI.

**Условия, в которых уместна адресная диагностика:**

- неизвестный формат/версия/операция, не покрытые достоверной записью capability matrix — однократный совместимый пробный вызов при первом использовании;
- явная ошибка, неожиданный пустой или повреждённый результат, недостающий выходной файл либо наблюдаемое противоречие ожидаемому эффекту;
- известный риск операции, которая может молча удалить, объединить или исказить объекты, либо получить некорректную размерность; проверять **именно этот инвариант**, не весь документ;
- разработка или изменение самого инструментального интерфейса — ограниченные fixture-based tests при его приёмке, **не** при каждом дальнейшем вызове.

**Минимальная диагностика:** сравнить конкретное ожидаемое постусловие (например, появился ли вставляемый объект, сохранились ли уникальные ID, верны ли мм и зазоры). `exit code 0` не доказывает эффект; изменение хеша/размера не доказывает эффект; неизменность файла сама по себе не означает `NO-OP`. Если объект уже соответствует постусловию, допустима корректная идемпотентность и переключение инструмента не требуется. Если операция доказанно не работает в известном режиме, использовать зарегистрированный fallback **без повторного воспроизведения дефекта**.

**Проверка перед сдачей:** один соразмерный контроль **готового артефакта** по предъявленным требованиям. Для обычной художественной задачи может хватить итогового SVG и одного preview; для нумерации — наличие номеров в правильных областях и соответствие палитре; для производства — измеряемые геометрические/масштабные ограничения и финальный print profile, если он заказан. Полный DOM-анализ, сравнительный рендер, тестирование всех PDF boxes и пересчёт каждой плитки применяются только к задачам, где соответствующий риск реален; не выполняются автоматически для всякой SVG-задачи.

**Доказательства и статусы:** `PASS` при подтверждённом конечном результате; `FAIL` при установленном нарушении; `UNPROVEN` при отсутствии достаточного наблюдения; `BLOCKED` при невозможности выполнить необходимое действие. Для локального сбоя можно использовать `UNSUPPORTED_INPUT`, `NO_OP_UNEXPECTED`, `INVALID_OUTPUT` и `EXECUTION_ERROR` — это **диагностические причины**, а не обязательные статусы каждого успешного CLI-вызова. В штатном task log достаточно команды/исполнителя и итоговых артефактов; детали диагностики сохранять лишь когда был реальный сбой, новый приём инструмента либо их требует пользователь.

**Контроль стоимости:** не вычислять SHA-256 без конкретной потребности в provenance/целостности. Если проверка неизменности пользовательского источника действительно нужна, достаточно одной контрольной пары до/после, а не множества хешей временных файлов. Не создавать отдельную QA-систему поверх уже работающих геометрических средств.

## 8. Реестр возможностей: данные, состояния, изменения

`docs/agent/capability-matrix.md` должен иметь два раздела: A) внешние CLI/API, библиотеки, tool-skills/harnesses; B) проектные CLI и runners. Для каждой строки минимум:

`capability_id · producer/type · version · platform/env · input contract · output contract · exact tested operation · invocation/entry point · status · verified_at · fixture/evidence ref · quirks + conditions · fallback · owner/origin`.

Статусы не путать: `DISCOVERED` (кандидат), `INSTALLED` (файл/программа есть), `PROBED` (вызвана операция), `VALIDATED` (результат прошёл QA), `UNSUPPORTED` (протокол не подходит), `BROKEN` (раньше работал, теперь не прошёл), `STALE` (версии/среда изменились), `NOT_TESTED`. Отдельными полями указывать **skill discovery** и **actual invocation**; `VALIDATED` для инструмента не означает, что главный Codex его выбрал автоматически.

**Bootstrap-кандидаты для локальной проверки (не утверждённые здесь состояния):** `inkscape.com` (сообщённая в исходном задании версия 1.4.4; path actions/export/query), `cli-anything-inkscape` (сообщённая 1.0.1; собственный JSON project, внешние SVG не читать), VTracer 0.6.15, Potrace 1.16, inkex 1.4.0, Shapely 2.2.0, vpype 1.15.0, ezdxf 1.4.5; project `tools/extensions/mosaic_labeler.py`, `tools/inkscape/precise_distribution.py`, `tools/coloring/package_coloring.py`. Каждый факт о наличии, версии и входе проверить локально, при отсутствии оставлять `NOT_TESTED/ABSENT`, не копировать как VALIDATED.

**Управление реестром:** добавлять только долговременно полезное наблюдение, которое меняет выбор маршрута. Однократный сбой помечать `OBSERVED` с краткими условиями, подтверждённый минимальным опытом или исходным кодом — `quirk`. Устаревшие записи помечать `STALE` по реально затронутому интерфейсу, а не отправлять на массовый retest всей среды. Не обновлять реестр после каждого успешного задания и не проверять уже подтверждённые баги снова. Коммит только в разрешённом Git scope.

## 9. Обслуживание `cli-anything-inkscape`

Для harness, рассчитанного на собственный JSON project, отправка внешнего SVG может приводить к `JSONDecodeError`; прямой headless Inkscape `paste-in-place` в некоторых условиях может возвращать `0` без вставки. Это наблюдения, требующие корректного указания происхождения. Если соответствующее ограничение уже подтверждено в действующей матрице для той же версии и среды, **повторный repro не нужен**: сразу выбрать совместимый маршрут. При отсутствии достоверного evidence — один минимальный тест только тогда, когда его исход влияет на выбор инструмента. Не путать проблему **формата harness** с проблемой **нативного action**.

- Оригинальный `.agents/skills/cli-anything-inkscape/SKILL.md` оставить неизменным (при external origin — исходная контрольная сумма).
- Создать `.agents/skills/cli-anything-inkscape/LOCAL_LIMITATIONS.md`: вход собственной JSON-модели, запрещённые сценарии открытия/модификации произвольного существующего SVG, проверенные допустимые операции, статус Boolean placeholders, ссылки на fixtures, альтернативные инструменты.
- В `AGENTS.md` и маршрутах запретить **безусловное** обращение к этой обёртке только из-за расширения `.svg`.
- Проверить, читает ли Codex дополнительный локальный документ в действительном workflow. Если сам skill не направляет к `LOCAL_LIMITATIONS.md`, добавить явный preflight в проектный операционный протокол или создать **отдельный** project wrapper skill с новым именем; не выдавать необнаруживаемый файл за эффективную политику.
- Для операций над существующим SVG выбирать нативный проверенный Inkscape CLI / библиотечный runner, а не несовместимый JSON harness. Для генерации с нуля использовать harness только в его подтверждённых пределах.

## 10. Компоновщик `Document Assembly`: функциональные требования

**Задача:** из готового художественного или производственного SVG, `palette_map.json`, при необходимости `tiles_manifest.json` и `layout.json` создавать итоговый редактируемый SVG-лист(ы), legend/explanatory blocks и preview/export. Компоновка **не** меняет форму/число зон, идентификаторы/цветовые соответствия и не создаёт новые тайлы.

**Точка входа:** существующий `tools/coloring/package_coloring.py`, после проверки фактического кода и вызовов. Предлагаемый CLI-контракт (корректировать лишь при документированной необходимости и тестах):

```text
package_coloring --artwork FILE --palette FILE --layout FILE
  [--tiles-manifest FILE] --out-svg FILE [--out-png FILE]
  [--out-pdf FILE] [--title TEXT] [--cols N]
  [--swatch-size VALUE] [--export-width PX]
```

Для каждого параметра определить единицы/семантику в `--help`: `--swatch-size` — page/layout units или физические единицы в explicit print profile, **не** тайловые mm; `--export-width` — только raster preview. Данные страницы (ширина/высота/поля/панели/шрифт/колонки/выравнивание/легенда) хранить в `layout.json` с указанным schema version. Любые пути, заголовки, размеры, координаты и конкретные названия артефактов приходят **из параметров**, не из ветки кода, посвящённой одному рисунку. При отсутствии required input — ошибка с объяснением, а не скрытое создание проекта Gum-Tree. Дефолты допускаются только нейтральные и документированные.

**Графические гарантии:**

1. Artwork встраивается недеструктивно с явно заданной матрицей `source viewBox → destination box`; никакой скрытой деформации или стирания источника.
2. Для вложения SVG с `defs`, IDs, CSS, fonts, masks, clipPaths и group transforms использовать проверенный способ импорта либо квалифицированно отказать; избегать коллизий ID/URL refs и потери inherited styles.
3. Палитра берётся из стабильной карты номеров; номера, образцы и подписи синхронизируются. Отсутствующий color/zone ID — контролируемая ошибка, не «цвет по позиции».
4. Легенда/экспликация укладываются в page bounds, не накладываются на artwork и не обрезаются. Длинные названия, кириллица, ≥1 page, нестандартный viewBox и пустые необязательные разделы — протестированные случаи.
5. Физическая печать `B→P` включается только по отдельному print profile, где проверяются мм, PDF boxes и масштаб 1:1. Обычная A→P компоновка листа **не** утверждает натуральную величину рисунка.
6. Финальный экспорт выполняет настоящий headless renderer; при приёмке нового/изменённого компоновщика проверить на fixtures корректность импорта, экспорта и типографики. В обычном задании достаточно проверить наличие готового листа и его визуальную пригодность; дополнительные проверки — только при конкретном риске.
7. Утилита пригодна для повторения на другом рисунке без изменения исходного кода и возвращает ненулевой exit code при неверных данных/ошибке.

Сохранить подтверждённую рабочую совместимость старых вызовов **только если** она не требует контекстного хардкода; иначе предложить явный `--legacy-profile`/адаптер с fixture и документированным breaking change, не выдавая несовместимость за сохранённую совместимость. Утилита не должна становиться универсальной SVG IDE или реализовывать собственный векторный движок.

## 11. Предметные skills: единство и границы

Создать/актуализировать проектные задания и при необходимости действительные `.agents/skills/<name>/SKILL.md` для:

1. `sketch-mosaic-pre-vectorizer` (A→A): линии/орнамент → редактируемые цветовые зоны.
2. `photo-mosaic-pre-vectorizer` (A→A): фотография кладки → очищенная художественная композиция.
3. `tessellation-mosaic-generator` (A→B): artwork → physical tiles with andamento, spacing, clipping и print only when demanded.
4. `vector-svg-to-numbered-contours` (A→A): **альтернатива 1**; SVG input adapter к реальному downstream `paintbynumbersgenerator`, не full rewrite.
5. `inkscape-cli-mosaic-labeler` (A→A): **альтернатива 2**; самостоятельный геометрический labeler на проверенных механизмах `inkex/Shapely/inkscape --query-all` или другом принятом headless пути.
6. `document-assembly` (A/B→P): готовая схема + palette/manifest → готовый лист с легендой; без изменения source geometry.

Для каждого: корректные frontmatter name/description (триггеры и отрицательные триггеры), реальный executable entry point или ссылка на проверенный инструмент, вход/выход/домен, описание ошибок и QA fixtures, evidence использования в главном Codex. Не объявлять все шесть принятыми, если часть реализуется отдельными задачами. Проектный рефакторинг вправе обновить описания существующих навыков и маршрут, но **не** обязан реализовать отсутствующий downstream двигатель или тайловый раскладчик в этом же изменении.

Действующие skills — прежде всего **исходные данные**; провести поиск прямых и косвенных упоминаний `cli-anything-inkscape`, `paste-in-place`, GUI, физических единиц и запретов на кодирование по всему текущему skill set. Удалить несовместимые обещания, сохранив настоящие договоры A/B и проверяемые особенности каждого навыка. Два labeler skills никогда не объявлять последовательными обязательными стадиями.

## 12. Приёмка и метод измерения

### 12.1. Проверки конфигурации и изменённых компонентов (однократная приёмка рефакторинга)

- Проверить синтаксис TOML, синхронизацию канонических инструкций с действительно активными значениями и отсутствие непреднамеренной смены trust/permissions. Это тест после изменения конфигурации, **не регулярная процедура каждой графической задачи**.
- Для изменённого маршрута выполнить один безопасный test case, который доказывает нужную операцию. Не обходить заново `--help` всех установленных CLI и не повторять все исторически известные ошибки.
- Для изменённого `package_coloring.py` достаточно **двух разнородных положительных примеров** (обычный лист и сложная легенда/иной `viewBox`) и **одного отрицательного** (некорректное соответствие палитры). Идемпотентность проверить повторным запуском только если контракт/код экспорта изменён и это свойство существенно. Существующий реальный предыдущий вызов использовать как regression вместо дополнительного искусственного fixture.
- Производственный B→P профиль проверять только если он реально изменяется или объявляется готовым в этой поставке. SVG raster/geometry/preview проверять **на итоговом fixture**, а не после каждой внутренней операции.
- Сохранить краткие результаты тестов, примеры входа/выхода и причину неуспеха, если он был. Постоянные SHA-256 временных файлов, независимый рендер каждого промежуточного шага, многократные DOM-diff и подробные командные транскрипты **не являются требованиями приёмки**.

### 12.2. Поведение основного Codex

В **одной чистой независимой сессии** целевого проекта проверить два репрезентативных задания без названия инструмента: (1) готовый цветной SVG → схема с номерами, (2) готовая схема с палитрой → итоговый лист. При существенном изменении доменной маршрутизации дополнительно выполнить **один** подходящий test case для A→B либо raster→A; не запускать всю матрицу из семи задач автоматически. Исходный baseline использовать, если он уже существует; **не** создавать отдельную дорогую baseline-сессию ради формального before/after.

Отметить только наблюдаемые факты: выбранный домен/маршрут, реально вызванный исполнитель, корректность итогового SVG/листа, отсутствие самовольного GUI, честную атрибуцию. Не требовать отдельных логов каждого CLI и full-chain QA. Если один из навыков ещё не реализован в scope проекта, указать `NOT_APPLICABLE` / `UNPROVEN`, а не имитировать его вызов. Для известного `NO-OP` проверить, что агент **не** вызывает заведомо неподдерживаемый action; многократное воспроизведение дефекта не требуется.

### 12.3. Статусы

`PASS`: тест выполнен и доказан соответствующими файлами/трассой. `FAIL`: измерено нарушение постусловий, исходных данных или границы домена. `UNPROVEN`: тест технически не проведён или доказательств недостаточно. `BLOCKED`: требуется конкретное разрешение/компонент/документ, без которого продолжать нельзя. `NOT_APPLICABLE`: сценарий сознательно вне текущей поставки; обоснование обязательно. Не писать `PASS` для задачи только за то, что skill создан на диске.

## 13. Последовательность исполнения и критерии перехода

**Stage 1 — Inventory & preservation.** Однократно инвентаризовать только затрагиваемые инструкции, маршруты, skills, компоновщик и известные записи матрицы; сохранить пользовательский Git status. **G1:** установлено, что реально существует и что разрешено изменять. Не сканировать и не хешировать весь репозиторий.

**Stage 2 — Canonical instructions & activation.** Выполнить содержательное проектирование четырёх уровней с первоочередным созданием полноценной Конституции мышления и операционного протокола по §3–4; провести содержательную сверку девяти требований §4.1 с прежним `developer_instructions`, установить новую редакцию в действующий ключ `.codex/config.toml`, согласовать `AGENTS.md`, проверить TOML/trust/загрузку и отсутствие инструментальной конкретики в Конституции. **G2:** главный Codex получает действительно переработанные, полноценные, разные по функции активные инструкции; покрытие обязательных правил продемонстрировано адресной сверкой, а не количеством изменённых строк или синтаксисом TOML. Без прохождения G2 не переходить к созданию реестра/утилит. Использовать существующее наблюдение о поведении как baseline, если оно есть; новый baseline необязателен.

**Stage 3 — Routes, contracts, matrix.** Реализовать требования §4.3–4.4 к карте по классам операций и двухсекционному реестру с сохранением исходных технических записей; описать A/B/P и действительные инструментальные ограничения, согласовать перекрёстные ссылки пяти skills. **G3:** нет ложного SVG→JSON harness, не перепутаны художественные зоны и физические тайлы, новый discovery выполняется лишь при отсутствии пригодного существующего маршрута.

**Stage 4 — Local tool compatibility.** Зафиксировать подтверждённые пределы чужого skill, сохранить upstream, сделать ограничения доступными Codex. **G4:** совместимый маршрут читается и не требует повторно вызывать дефектный инструмент.

**Stage 5 — Document Assembly.** Параметризовать имеющийся компоновщик, задать layout schema, выполнить ограниченные тесты §12.1. **G5:** на двух различных художественных fixtures создаётся годный лист без предметного хардкода, некорректный input отвергается.

**Stage 6 — Targeted behavioral acceptance.** Провести сценарии §12.2 в одной чистой сессии, исправить только выявленные дефекты. **G6:** выбор инструмента и конечный результат наблюдаемо соответствуют задаче; штатная работа не обрастает повторными промежуточными проверками.

**Stage 7 — Delivery.** Scoped diff и `git diff --check`, сохранность исходников, рабочие ссылки, краткий report, разрешённый коммит. **G7:** заказчик получает реальные выходные файлы и честные статусы без лишней диагностической документации.

**Stage** — законченный блок изменений с наблюдаемым итогом, а не разрешение на бесконечные циклы self-QA. При FAIL устранять конкретный дефект и повторять соответствующий тест, **не** начинать полный цикл приёмки заново.

## 14. Состав поставки

При успешном выполнении должны существовать реальные, проверенные файлы (точные пути согласовать с фактической структурой репозитория, не плодить копии):

- `.codex/config.toml` и `AGENTS.md`, канонические `docs/agent/graphics-developer-instructions.md` и `graphics-model-behavior.md` плюс проверка согласованности;
- `docs/agent/README.md`, `graphics-data-contracts.md`, `capability-matrix.md`, краткая `instruction-layers-decision.md` и восстановление среды;
- `.agents/skills/cli-anything-inkscape/LOCAL_LIMITATIONS.md` при наличии этого внешнего skill, неизменный upstream SKILL и договорённость о способе его project-use;
- обнаруживаемый `.agents/skills/document-assembly/SKILL.md` при наличии проверенного компоновщика, корректировки существующих mosaic SKILL.md по области действия;
- `tools/coloring/package_coloring.py` (либо обоснованно выбранный другой existing location), schema/config и fixture-based tests, только если код действительно присутствует и требует рефакторинга;
- минимальные fixtures для изменённых интерфейсов, итоговые SVG/preview и краткая запись о blind-проверке основного Codex; развернутые logs/hashes — только для подтверждённого дефекта;
- короткий итоговый report `docs/agent/refactor-acceptance-v4_2.md`: изменённые файлы и маршруты, результаты ограниченных тестов, оставшиеся риски, реальное происхождение инструментов и сведения о коммите. Не переписывать весь terminal trace.

**Сохранять в репозитории только оправданные файлы.** Большие временные PNG/logs можно архивировать или не коммитить по действующей политике, но evidence приёмки должен быть доступен, а ключевые редактируемые результаты — сохранены. Не включать чужие пользовательские изменения в итоговый commit.
