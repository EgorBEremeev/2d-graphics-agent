# Project Brief — `photo-mosaic-pre-vectorizer`

**Версия:** 4.2 · **Дата:** 11.11.2026  
**Тип:** самостоятельное задание на проектный Codex Agent Skill  
**Проект:** `C:\gitCreative\solo-learn-mosaic` · **Режим:** воспроизводимый headless raster→vector workflow.

**Режим проверок:** штатный вызов уже подтверждённого маршрута не сопровождается повторным `--help`, discovery, хешированием промежуточных файлов, DOM-diff после каждой команды или независимым рендером каждой стадии. Тестовые fixtures ниже предназначены для **однократной приёмки нового/изменённого навыка** и адресной регрессии после изменения его контракта. В обычном задании выполняется минимальная проверка конечного результата; промежуточная диагностика — при неизвестном интерфейсе, наблюдаемом сбое или реальном риске потери геометрии/масштаба. Не создавать подробный QA-log при штатном успешном исполнении.

## 1. Функция и границы

Подготовить специализированную компетенцию восстановления **художественных цветовых областей из фотографии реально существующей мозаики**. Фото содержит физические tesserae, старые швы, тени, рельеф, блики, потери поверхности, перспективу и освещение; они не обязаны совпадать с содержательными границами будущей композиции. Результатом являются самостоятельные художественные зоны изображения, не копии всех старых плиток.

Skill не очищает простой линейный эскиз, не создает новую раскладку тайлов, не назначает новое grout, не изготавливает PDF 1:1, не нумерует области и не компонует финальный лист. Даже если на фото есть линейка/знакомый прямоугольник, параметры перспективы **не становятся** автоматически физическими размерами нового изделия.

## 2. Вход и результат

**Вход:** фотография `jpg/png/tiff`, optional границы кадра/маски, перспективные ориентиры, художественные подсказки палитры, флаги сохранения значимых деталей, разрешение и тип покрытия. Источник неизменен.

**Домен A:** координаты исходного растра или исправленного перспективного raster, затем нормализованный SVG `viewBox`; матрицы `source→rectified→artwork` документировать. Визуальное сравнение допускает обратную проекцию на исходную фотографию, чтобы обнаруживать неверное выпрямление.

**Выходы:**

- `artwork_regions.svg` — замкнутые редактируемые художественные зоны с `zone_id`/`color_id` и стабильной палитрой; видимые старые швы/блики не должны порождать ложные зоны при отсутствии художественного смысла.
- `artwork_regions.manifest.json` — image size, projective transform/homography либо `identity`, segmentation settings, affected mask regions, palette mapping, confidence/ambiguity per zone, provenance и QA.
- `flattened_regions.png`, `segmentation_preview.png`, `preview_overlay.png`, `qa_summary.json` — диагностический растр, сопоставление и топологическая оценка, с фиксированными параметрами повторения.

Имя `C_lay_boundaries.svg` возможно только для копии тождественной **artwork** семантики. Никаких физических `tile_id`, mm, grout, offsets or PDF page box по умолчанию.

## 3. Инструментальная стратегия

При первичной разработке/смене исполнителя сверить `AGENTS.md`, route map и capability matrix; в штатной задаче использовать уже подтверждённые записи без повторной диагностики версий и `--help`. Возможные исполнители: ImageMagick для ослабления текстуры/морфологии, подходящий raster CLI/библиотека для perspective warp и segmentation, VTracer или Potrace при соответствующем типе масок, реальный Inkscape CLI для SVG операций, проверенный parser/geometric library для topology QA.

Не выдавать `cli-anything-gimp` за весь GIMP: сначала выяснить фактические команды и зависимость от Pillow/renderer. `cli-anything-inkscape`, если установленный harness принимает только собственный JSON, **не** использовать как reader/editor существующего SVG; прямой native Inkscape CLI независим от него. CLI-Hub участвует в discovery, но не является движком сегментации. `--help` и наличие `SKILL.md` не подтверждают ни реально работающий алгоритм, ни выбор агентом.

При отсутствии пригодного подтверждённого способа: на одном репрезентативном фото сравнить два подхода, например (a) corrected raster→VTracer segmentation и (b) guided masks/regions→trace; проверить потерю тонких осмысленных линий, ложные зоны старых швов, перспективную ошибку, число ложных островов, palette stability и ремонтопригодность. Порог сглаживания задаётся в **image pixels по толщине фотографических швов**, не в мм будущей плитки. Если корректно восстановить структуру невозможно, признать неопределённость и сохранить маску/область review.

`reuse → adapt → build narrow gap`: допускаются воспроизводимые узкие функции для корректировки перспективы, масок, преобразования результатов и проверки, но не бездоказательный новый общий raster segmentation engine. Новые project utilities обязаны иметь CLI/config, независимость от названия фотографии и tests.

## 4. Требования к workflow и skill

Создать/актуализировать `.agents/skills/photo-mosaic-pre-vectorizer/SKILL.md` с frontmatter `name`/`description`; триггер: *photograph of existing physical mosaic, smalt/tesserae image to artistic regions*; исключения: clean sketch, svg labeling, physical tiling, document assembly.

**Пошаговый рабочий контракт:**

1. Инспектировать фото и отличить художественные границы от старых швов, теней, трещин и бликов. Обозначить зоны uncertainty.
2. Если перспектива искажает контуры, выполнить rectification по проверенной модели (не объявлять произвольную homography истиной без anchors/QA). Фиксировать координатную трансформацию и правила cropping.
3. Применить только доказанные фильтры шумоподавления/ослабления старых швов; сохранить резкие границы значимых цветовых масс. Указать параметры и порядок обработки.
4. Сегментировать композицию. Сверить версии/flags VTracer через настоящий `--help`; названия watershed/cutout не превращать в гарантию качества.
5. Векторизовать полученные зоны; нормализовать shared boundaries, holes, transforms, fill-rule и видимость; каждую зону обеспечить стабильным ID и цветом.
6. Сравнить результат с фото и исправленным raster, измерить ложные зоны, утраченные художественные элементы, неоднозначности и топологию. При FAIL изменить метод.
7. Сформировать SVG, manifest, previews и machine QA, разграничить `RECOVERED / NEEDS_REVIEW / FAILED` по зонам.

Не обещать восстановление скрытых за бликом или повреждением границ. Если пользователь поставил задачу реставрационной реконструкции, отличать подтверждённые области от гипотетической дорисовки.

## 5. Acceptance fixtures и outcome

| Fixture | Содержание | Обязательная проверка |
|---|---|---|
| P1 | Равномерно освещённая кладка, крупные художественные поля и контрастные старые швы | Швы не становятся ложными художественными регионами; сохраняются цветовые области |
| P2 | Бликующая/неровная смальта и мелкая фактура | Сохранение существенных границ при подавлении локального шума; конкретные неопределённости |
| P3 | Наклонный снимок с опорными линиями/углами | Корректность inverse warp, сохранение пропорций в rectified image, overlay |
| P4 | Скрытые участки, неразличимая палитра | `NEEDS_REVIEW/UNPROVEN`, не произвольное восстановление |
| P5 | Фото с известным физическим размером старой кладки | Отсутствие самовольного физического масштаба нового SVG/изделия |

**Контроль результата:** оценить готовые художественные зоны по замкнутости, цветам/IDs и одному итоговому photo/overlay; специфический анализ holes/overlaps применять при соответствующих симптомах. Для каждой промежуточной команды проверки не нужны. В отчёте различать штатный CLI и newly built runner.

При приёмке маршрута в общей новой сессии основного Codex пользователь просит преобразовать фотографию мозаики **без названия skill/CLI**. PASS требует самостоятельный выбор photo-маршрута, вызов реально пригодных инструментов и QA; запуск sketch-маршрута/генератора тайлов без обоснования — FAIL.

## 6. Этапы, поставка, ограничения

**Stage 1:** inventory, действующие skills/tools и доступность интерфейсов → **Gate:** локальный, не бумажный, список кандидатов.  
**Stage 2:** comparison of 2 segmentation/trace workflows → **Gate:** измеренное решение и сохранённые промежуточные изображения.  
**Stage 3:** input/coordinate contract, zones and manifest → **Gate:** P1/P3 валидны.  
**Stage 4:** Skill + CLI integration, masks/uncertainty handling → **Gate:** repeatable invocation.  
**Stage 5:** P1–P5 и независимый new-session test → **Gate:** evidence/QA.  
**Stage 6:** scoped Git, обновление подтверждённых capabilities, минимальная документация восстановления.

Работающие прежние компоненты сохранять; если skill ещё отсутствует, не объявлять всю 2D-конфигурацию дефектной — эта предметная реализация является самостоятельной задачей. Поставка: обнаруживаемый Skill, выбранный executor/params, реальные SVG/manifests/diagnostics, тесты, записи о подтверждённых ограничениях и trace.
